# نقشه راه جامع جیبیک (Jibik) — سند مرجع محصول، طراحی و پیاده‌سازی

**نسخه سند:** 1.0  
**وضعیت:** برنامه مصوب برای شروع توسعه؛ هنوز به معنای پیاده‌سازی امکانات نیست  
**مخزن:** https://github.com/qashqaeii/Jibak  
**پلتفرم اول:** Android Native با Kotlin و Jetpack Compose  
**هدف انتشار:** کافه‌بازار و در آینده کانال‌های توزیع بیشتر  
**هویت محصول:** جیبیک؛ دستیار هوشمند و دوست‌داشتنی مدیریت مالی شخصی و خانوادگی، با کاراکتر روباه «جیبو»

## 1. تعهدها و الزامات غیرقابل مذاکره

1. ساخت صفر تا صد محصول به‌صورت گام‌به‌گام در همین مخزن؛ هر فاز با خروجی واقعی، تست و Commit مشخص. گزارش کار باید «انجام‌شده» را از «برنامه‌ریزی‌شده» تفکیک کند.
2. Android کاملاً Native؛ Kotlin، Jetpack Compose، RTL فارسی، تومان در نمایش، تاریخ شمسی؛ طراحی قابل توسعه برای تبلت و آینده iOS/وب از طریق API مستقل.
3. طراحی نهایی از نظر شخصیت، رنگ، فرم و ترکیب‌بندی دقیقاً مبتنی بر دو موکاپ موبایل مورد تأیید گفتگو: «خوش‌آمدگویی با روباه نارنجی» و «داشبورد مالی با کارت سبز تیره، کارت‌های درآمد و هزینه، نمودار، دکمه نارنجی ثبت و نوار پایین». **تصویر سایت دسکتاپ مرجع UI اندروید نیست.**
4. روباه نارنجی جیبو با هودی سبز، شخصیت رسمی برند است؛ نه کیف پول بنفش و نه شخصیت انسانی. کاربردش در راهنمایی، موفقیت، وضعیت خالی و نکته‌های کوتاه است، نه تزئین بیش از حد صفحات مالی.
5. همه تصویرهای رستری لازم (حالت‌های جیبو، آنبوردینگ، Empty State و تصاویر نشان‌دار) به WebP بهینه تبدیل و با نام‌گذاری منظم داخل مخزن قرار می‌گیرند. نمودارها، متن، کارت‌ها و کنترل‌ها باید **واقعاً در Compose پیاده شوند**، نه به‌صورت عکس ثابت از UI.
6. معماری Offline-first، ذخیره امن محلی، همگام‌سازی چنددستگاهی و اشتراک‌گذاری خانوادگی با مرزبندی حریم خصوصی.
7. محصول عمومی، قابل استفاده برای تک‌نفره و خانواده، از ابتدا آماده رشد کاربران، پشتیبانی، داده‌برداری و اجرای عملیاتی.
8. از ابتدا آمادگی انتشار و به‌روزرسانی در کافه‌بازار، ثبات applicationId و کلید امضا، تولید APK و آینده‌پذیری فروش اشتراک/لایسنس؛ کلید خصوصی هرگز در Git ثبت نشود.
9. CI روی GitHub Actions از مراحل ابتدایی: Build، Lint، Test، خروجی APK قابل دریافت؛ Release امضاشده پس از تنظیم Secrets؛ اعتبارسنجی انتشار با چک‌لیست.
10. هر صفحه باید حالت‌های Loading، Empty، Error، Offline، Success و Accessibility داشته باشد؛ هیچ صفحه نیمه‌کاره یا دکمه تزئینی در نسخه قابل تحویل نباشد.
11. زبان متن‌ها دوستانه، کوتاه، فارسی روان و صادقانه؛ بدون سرزنش کاربران درباره خرید و بدون نمایش اطلاعات ساختگی به‌عنوان داده واقعی.
12. تغییرات به ترتیب وابستگی، با طراحی و تست سناریوهای مرتبط، Commitهای قابل رهگیری و یادداشت مهاجرت دیتابیس/API انجام می‌شوند.

## 2. چشم‌انداز محصول و سناریوهای پایه

جیبیک فقط نرم‌افزار ثبت هزینه نیست؛ یک مرکز مالی خانوادگی است که چهار سؤال را سریع پاسخ دهد: «چقدر دارم؟»، «کجا خرج شده؟»، «چقدر می‌توانم خرج کنم؟»، «برای هدف و تعهد بعدی آماده‌ام؟»

**سفر کاربر فردی:** نصب → معرفی کوتاه → شروع آفلاین یا ساخت حساب → انتخاب واحد پول و روز شروع ماه → ساخت حساب (کارت، نقد، پس‌انداز) → ثبت اولین هزینه در چند لمس → مشاهده گزارش → بودجه و هدف مالی.

**سفر زوج/خانواده:** ساخت خانواده → دعوت عضو با تأیید → تعیین دسترسی → افزودن حساب مشترک و حساب خصوصی → ثبت هزینه توسط دو دستگاه → Sync → گزارش هزینه‌های مشترک و بودجه → فهرست خرید مشارکتی → اعلان تعهدات و اهداف مشترک.

**سفر تجاری آینده:** کاربر رایگان → دیدن امکانات اضافه و توضیح ارزش → خرید اشتراک از کانال مجاز → تأیید خرید در سرور → فعال‌شدن Entitlement → تمدید، بازیابی خرید، لغو، انقضا و بازگشت به امکانات رایگان بدون حذف داده‌ها.

## 3. سند هویت بصری و Design System

### 3.1 DNA تصویری ثابت

- جهت راست‌به‌چپ واقعی؛ متن‌ها، آیکون‌های جهت‌دار، نمودارها و ناوبری با RTL هماهنگ باشند.
- پس‌زمینه روشن کرم/سفید گرم؛ فضای تنفس حساب‌شده؛ کارت‌های نرم، سایه بسیار لطیف؛ سبک شاد اما پریمیوم، نه کودکانه.
- سبز جنگلی/یشمی عمیق برای کارت موجودی و برند؛ سبز نعنایی برای درآمد و موفقیت؛ نارنجی گرم برای CTA اصلی و جیبو؛ قرمز مرجانی کنترل‌شده برای هزینه؛ رنگ‌های ثانویه فقط برای نمودار و دسته‌بندی.
- اعداد مالی بزرگ، خوانا، با جداکننده هزارگان و برچسب واحد؛ نمایش/مخفی‌سازی موجودی.
- نمونه پالت اولیه برای پیاده‌سازی (پس از نمونه‌برداری از موکاپ‌ها و Screenshot QA تثبیت می‌شود): BrandDark=#07574C؛ BrandDeep=#013F38؛ Mint=#21C79B؛ Orange=#FF8A1F؛ Background=#FFFAF5؛ Surface=#FFFFFF؛ Text=#102D31؛ Expense=#E95C50؛ Border=#ECE8E2. این مقادیر «پیشنهادی آغازین» هستند، نه ادعای استخراج دقیق از تصویر.
- تایپوگرافی با فونت فارسی دارای مجوز باز (ترجیحاً Vazirmatn) و اعداد فارسی؛ رعایت مقیاس فونت سیستم. مقادیر قابل جستجو، کپی و انتخاب باقی بمانند.
- فاصله‌ها بر پایه گام‌های 4/8/12/16/24/32dp؛ حداقل ناحیه لمس 48dp؛ شعاع کارت‌های اصلی 20–24dp، کارت‌های فرعی 14–18dp؛ انیمیشن‌های 150–300ms با پشتیبانی Reduced Motion.
- Dark Mode کامل در فاز نهایی طراحی می‌شود، با کنتراست واقعی، نه معکوس ساده رنگ‌ها.

### 3.2 صفحه‌های مرجع تصویری و محل استفاده جیبو

- **صفحه خوش‌آمدگویی:** لوگوی جیبیک، تیتر کوتاه، جیبو در مرکز با موبایل، سه مزیت مختصر، CTA سبز «شروع کنیم»، ورود به حساب؛ بدون شلوغی.
- **داشبورد Home:** بالا لوگو/اعلان و احوالپرسی؛ کارت بزرگ موجودی سبز تیره با امکان مخفی کردن؛ دو کارت درآمد و هزینه ماه؛ کارت‌های بودجه و ترکیب هزینه؛ اکشن‌های ثبت سریع؛ آخرین تراکنش‌ها؛ Bottom Navigation ثابت. جیبو به اندازه محدود، در هدر یا کارت «پیشنهاد جیبو» حضور داشته باشد و فضای اعداد را نگیرد.
- **حالت‌های مکمل جیبو:** خوشحال، فکرکن، هشدار دوستانه، جشن هدف، لیست خرید، بودجه نزدیک سقف، آفلاین و بدون داده. همه با تناسب اندام، چشم‌ها، گوش‌ها، لباس، رنگ‌ها و هویت ثابت.
- برای دارایی‌های تصویری پوشه‌های assets/source، android/core/designsystem/src/main/res/drawable-nodpi و docs/design/references ایجاد شود؛ فایل منبع و WebP بهینه جدا باشند.
- حداقل دو اندازه مرجع گوشی (تقریباً 360dp و 412dp)، بررسی گوشی کوچک، بزرگ و Font Scale بالا، تصویربرداری Visual Regression و تأیید وفاداری به موکاپ.

### 3.3 اجزای قابل استفاده مجدد

JibikTopBar، JibikBalanceHero، MoneyAmount، KPI Card، BudgetProgress، CategoryDonut، TransactionRow، QuickAction، JiboTipCard، EmptyState، SmartBottomSheet، PersianAmountField، JalaliDatePicker، CategoryPicker، HouseholdSwitcher، FilterChips، AlertBanner، Paywall، BottomNavigation، LoadingSkeleton، ConfirmationDialog.

## 4. نقشه کامل صفحه‌ها و معماری حرکت کاربر

**ورود:** Splash → معرفی سه‌اسلایدی اختیاری → ورود/ثبت‌نام OTP یا شروع محلی → ایجاد حساب اولیه → انتخاب حالت فردی/خانوادگی → خانه.

**ناوبری اصلی RTL:** خانه | تراکنش‌ها | دکمه مرکزی «+» (افزودن) | گزارش‌ها | بیشتر.

**خانه:** مانده واقعی حساب‌های مجاز، درآمد/هزینه، بودجه، دسته‌های پُرهزینه، تراکنش‌های اخیر، پیشنهاد مختصر جیبو، نمایش وضعیت همگام‌سازی.

**تراکنش‌ها:** تاریخچه، جست‌وجو، فیلترهای تاریخ/حساب/دسته/عضو/مبلغ، ویرایش، کپی، حذف امن، پیوست، جزئیات تفکیک‌شده، تراکنش انتقال و بازپرداخت.

**افزودن سریع:** انتخاب هزینه/درآمد/انتقال → مبلغ → دسته/حساب → ثبت؛ گزینه «جزئیات بیشتر»: چند قلم خرید، محل، یادداشت، عکس فاکتور، تکرار، برچسب، مالک هزینه.

**گزارش‌ها:** روز/هفته/ماه شمسی/بازه سفارشی، جریان نقدی، نمودار دسته، مقایسه دوره، روند، اعضا، بودجه و خروجی.

**بیشتر:** حساب‌ها و کیف‌ها، دسته‌ها، بودجه‌ها، اهداف پس‌انداز، فهرست خرید، قبوض/اقساط/وام، بدهی/طلب، خانواده، تقویم مالی، اعلان‌ها، اشتراک، پروفایل، امنیت، پشتیبان‌گیری و خروجی، راهنما، درباره ما، حریم خصوصی.

**صفحات تجاری:** معرفی پلن‌ها/Paywall، جزئیات پلن، وضعیت اشتراک، سوابق خرید، بازیابی خرید، ارتقا/تمدید، راهنمای پرداخت و لغو.

**صفحات پشتیبانی/عملیاتی:** ارسال بازخورد، گزارش خطا با حذف داده حساس، درخواست خروجی/حذف حساب، مرکز اعلان‌ها، خطاهای شبکه و بازیابی نشست.

## 5. ماژول‌های دامنه و امکانات کامل

### 5.1 حساب‌ها و دارایی‌های روزمره

- حساب بانکی دستی (بدون اتصال مستقیم به بانک در نسخه اولیه)، پول نقد، کیف پول، پس‌انداز و حساب مشترک؛ موجودی آغازین و اصلاح موجودی با دلیل.
- وضعیت فعال/بایگانی، انتخاب رنگ/آیکون، ترتیب حساب‌ها، پنهان‌سازی موجودی؛ جمع‌زدن فقط حساب‌های قابل رؤیت.
- انتقال بین حساب‌ها «هزینه» نیست؛ جابه‌جایی حساب خصوصی/مشترک با مجوز و ثبت سمت‌های صحیح.

### 5.2 درآمد و هزینه

- حقوق، پاداش، درآمد جانبی، هدیه، بازپرداخت، فروش و درآمدهای سفارشی.
- ثبت هزینه فوری با حساب، تاریخ شمسی، برچسب، توضیح و پیوست.
- خریدهای چندقلمی: یک رسید فروشگاه با چند ردیف دسته‌بندی‌شده؛ مجموع ردیف‌ها باید دقیقاً برابر مبلغ تراکنش باشد و تنها **یک بار** از موجودی کسر شود.
- تراکنش تکراری، وضعیت برنامه‌ریزی‌شده/ثبت‌شده، بازگشت وجه/ابطال، شناسایی موارد تکراری قبل از ثبت نهایی.
- یادداشت، فروشگاه، مخاطب اختیاری و جست‌وجوی سریع؛ ورود دسته‌ای CSV با پیش‌نمایش و تأیید کاربر.

### 5.3 طبقه‌بندی سه‌سطحی قابل ویرایش

- خوراک و خرید منزل: حبوبات؛ سبزیجات؛ میوه؛ کربوهیدرات (برنج، نان، ماکارونی، سیب‌زمینی)؛ پروتئین (گوشت، مرغ، ماهی)؛ لبنیات؛ تخم‌مرغ؛ تنقلات؛ نوشیدنی؛ چاشنی‌ها و روغن؛ شوینده‌ها؛ غذای بیرون.
- مسکن: اجاره، شارژ ساختمان، تعمیرات، لوازم منزل، اقلام مصرفی و نگهداری.
- قبوض و ارتباطات: آب، برق، گاز، تلفن، اینترنت، موبایل، اشتراک سرویس‌ها؛ سررسید و اعلان.
- حمل‌ونقل: سوخت، تاکسی/تاکسی اینترنتی، حمل‌ونقل عمومی، تعمیر، بیمه، عوارض، پارکینگ.
- سلامت، بهداشت و زیبایی: پزشک، دارو، آزمایش، دندان‌پزشکی، بهداشت و مراقبت.
- پوشاک و خرید شخصی؛ آموزش و فرزندان؛ تفریح و سفر؛ خانواده و هدایا؛ حیوانات خانگی؛ خیریه؛ مالیات و عوارض؛ سایر موارد.
- بازپرداخت و اقساط به‌عنوان تعهد/جریان پول مدل شوند تا هنگام ثبت بدهی اولیه، دریافت و تسویه دو بار هزینه محسوب نشود.
- دسته پیش‌فرض قابل اصلاح، دسته شخصی/خانوادگی سفارشی، مرتب‌سازی، بایگانی و نگاشت دسته برای گزارش تاریخی.

### 5.4 بودجه‌ها و هشدارها

- سقف ماهانه/هفتگی/شمسی برای کل و دسته، شخصی یا خانوادگی، بودجه قابل انتقال به دوره بعد (اختیاری).
- درصد مصرف، باقی‌مانده، پیش‌بینی مصرف تا پایان دوره و هشدارهای 70/90/100 درصد قابل تنظیم.
- تفکیک هزینه واقعی از پرداخت برنامه‌ریزی‌شده و نشان دادن «مبلغ قابل خرج» با قواعد روشن.

### 5.5 خرید هوشمند خانواده

- فهرست مشترک با افزودن قلم، مقدار، واحد، قیمت تخمینی، تیک‌زدن هم‌زمان و تاریخچه.
- دسته خودکار پیشنهادی قابل اصلاح؛ ثبت قیمت واقعی هنگام خرید؛ تبدیل قلم‌های خریداری‌شده به یک تراکنش چندردیفی فقط با تأیید نهایی و بدون دو‌بارشماری.
- فهرست‌های تکرارشونده هفتگی، فروشگاه‌های دلخواه، تغییرات قیمت خریدهای قبلی؛ عدم ادعای قیمت زنده بازار بدون منبع معتبر.

### 5.6 اقساط، بدهی و تعهدات

- وام/بدهی/طلب با اصل مبلغ، پرداخت‌های ثبت‌شده، سررسید، اقساط، وضعیت تسویه و یادآوری.
- قبض‌های دوره‌ای، اجاره، قسط، اشتراک نرم‌افزار، پرداخت‌های دوره‌ای.
- ثبت پرداخت از یک حساب واقعی، ارتباط با تعهد و جلوگیری از احتساب مضاعف؛ اعلان سررسید شمسی.

### 5.7 اهداف پس‌انداز

- هدف شخصی/مشترک با مبلغ، تاریخ، اولویت، تصویر/آیکون، پیشرفت و سهم هر عضو.
- «پیشرفت هدف» با انتقال/اختصاص موجودی واقعی یا ثبت مشارکت مشخص؛ از ایجاد پول موهوم جلوگیری شود.
- محاسبه مبلغ لازم در هر ماه و سناریوهای رسیدن به هدف.

### 5.8 خانواده و دسترسی‌ها

- ایجاد چند فضای مالی: شخصی و خانوادگی، دعوت و خروج عضو، انتقال مالکیت با تأیید.
- نقش‌های مالک، ویرایشگر و مشاهده‌گر با کنترل صریح دسترسی به حساب‌ها، تراکنش‌ها، هدف‌ها و بودجه‌ها.
- حریم خصوصی «پیش‌فرض خصوصی»: هیچ تراکنش شخصی به خانواده منتقل نشود مگر کاربر آن را عمداً مشترک کند.
- نمایش نویسنده/ویرایش‌کننده رویداد و تاریخچه تغییرات حساس، مدیریت تعارض و حذف/بازگشت دسترسی.
- گزارش‌های خانوادگی فقط از داده‌های مشترک و مجاز محاسبه شوند.

### 5.9 گزارش‌ها و بینش‌ها

- گردش پول، هزینه به تفکیک دسته/عضو/حساب، روند چندماهه، مقایسه دوره، نرخ پس‌انداز و نمودار بودجه.
- Drill-down از نمودار به ردیف تراکنش‌ها، فیلتر ترکیبی، خروجی CSV و PDF، گزارش اشتراک‌پذیر بدون افشای داده‌های خصوصی.
- تقویم مالی شمسی، خلاصه هفته/ماه، مقایسه بودجه با واقعیت؛ پیشنهادهای محاسباتی قابل توضیح.

### 5.10 دستیار جیبو و قابلیت‌های هوشمند

- مرحله اول: پیام‌های Rule-based و بدون API خارجی؛ هشدار دوستانه، خلاصه ماه، اقدام پیشنهادی متناسب با داده واقعی.
- مرحله بعد: OCR فاکتور با تأیید کاربر، پیشنهاد دسته‌بندی، ورودی متنی/صوتی، پرسش از داده‌های خود کاربر، پیش‌بینی جریان نقدی با افق و فرض مشخص.
- دستیار **هرگز بدون تأیید نهایی کاربر تراکنش مالی ثبت یا تغییر ندهد**؛ دسترسی داده حداقلی و شفاف، هزینه/سقف مصرف AI و قابلیت خاموش‌کردن.
- مدل و سرویس AI قابل تعویض در بک‌اند؛ ورود اطلاعات محرمانه به سرویس ثالث فقط با اطلاع/رضایت و سیاست نگهداری مشخص.

### 5.11 تنظیمات و قابلیت‌های عمومی

- تاریخ شمسی، واحد تومان/ریال در نمایش، ترجیح آغاز هفته و ماه مالی، قالب اعداد، تم روشن/تیره و دسترس‌پذیری.
- PIN/بیومتریک، قفل برنامه پس از خروج، کنترل اعلان، زبان فارسی، خروجی/پاکسازی داده، جست‌وجو، راهنما، پشتیبانی و گزارش خطا.
- Widget صفحه اصلی و Shortcuts برای «افزودن هزینه» در فاز تکمیلی؛ بهینه‌سازی عملکرد و مصرف باتری.

## 6. قواعد غیرقابل نقض صحت مالی

1. **واحد ذخیره محاسباتی:** ریال صحیح 64 بیتی در Android و bigint در PostgreSQL؛ نمایش پیش‌فرض تومان با تبدیل صریح. برای پول از float/double استفاده نمی‌شود. ارقام و ورودی‌ها اعتبارسنجی و محدوده عدد بررسی می‌شوند.
2. مدل دفترکل دوطرفه/انتقال اتمیک: مجموع اثر سمت‌های هر رویداد مالی متوازن است؛ درآمد، هزینه، انتقال، بازپرداخت و اصلاح موجودی قواعد جدا دارند.
3. Split یک خرید فقط طبقه‌بندی همان تراکنش است؛ یک تراکنش اصلی با چند ردیف، نه چند برداشت مضاعف. مجموع Split برابر مبلغ کل.
4. رویدادهای مالی شناسه یکتا و idempotency key دارند؛ retry یا همگام‌سازی مجدد نباید تراکنش تکراری بسازد.
5. ویرایش پس از ثبت با سابقه تغییر و اصلاح محاسباتی انجام می‌شود؛ حذف حساس یا بازگشت وجه با رویداد معکوس قابل ردیابی، نه دست‌کاری بی‌اثر دفترکل.
6. همه زمان‌ها روی سرور UTC ثبت می‌شوند و در UI شمسی/Asia-Tehran بر اساس ترجیح کاربر تبدیل می‌شوند؛ سررسیدهای محلی هنگام DST/تغییر منطقه زمانی تست شوند.
7. داده فردی و خانواده Tenant/Scope مستقل دارد؛ API باید در سطح QuerySet و شیء، مجوز کاربر را اعمال کند، نه فقط مخفی‌سازی در UI.
8. Offline write ابتدا در Room ثبت، سپس در Outbox ارسال می‌شود؛ سرور مرجع نهایی اعتبارسنجی و تضاد دسترسی است. وضعیت pending/failed/synced در UI شفاف باشد.
9. تعارض رکوردهای مالی بدون Last-Write-Wins کورکورانه؛ ورود هم‌زمان و ویرایش هم‌زمان با versioning، شناسه رویداد و مسیر رسیدگی/ادغام مشخص شوند.
10. جابه‌جایی بین حساب‌ها، اختصاص پس‌انداز و تسویه بدهی باید در داشبورد بدون احتساب دوباره لحاظ شوند.

## 7. معماری فنی پیشنهادی

**Android:** Kotlin + Jetpack Compose + Material 3 سفارشی‌سازی‌شده + Navigation Compose؛ MVI/UDF با ViewModel، StateFlow، Coroutines؛ Hilt؛ Room + DataStore؛ Retrofit/OkHttp + Kotlin Serialization یا Moshi؛ WorkManager برای Sync و یادآوری؛ کتابخانه تست Compose؛ Dependency Versions Catalog. نسخه‌های وابستگی در زمان شروع هر فاز قفل و مستند می‌شوند.

**Backend:** Django + Django REST Framework + PostgreSQL + Redis + Celery؛ JWT access کوتاه‌مدت و refresh قابل ابطال یا نشست امن متناسب با OTP؛ Django Admin اختصاصی برای پشتیبانی و محصول؛ فایل‌ها در Object Storage خصوصی؛ OpenAPI با versioning.

**مرزبندی:** Client مالک UI و cache است، سرور مرجع مجوزها/اشتراک و داده مشترک؛ **هیچ حساب بانکی واقعی، برداشت خودکار یا اتصال بانکی بدون رضایت و مجوز لازم در نسخه اولیه پیاده نمی‌شود**.

**ساختار پیشنهادی مخزن:**

- android/app — app، navigation و build variants
- android/core/designsystem — تم و کامپوننت‌ها
- android/core/model — مدل‌های مشترک و Money
- android/core/database — Room، migrationها
- android/core/network — API و auth
- android/core/data — repositories و sync
- android/core/domain — use cases
- android/core/common — تاریخ شمسی، اعداد، نتیجه/خطا
- android/core/billing — رابط فروشگاه و Entitlement
- android/feature/* — onboarding, home, transactions, accounts, budgets, goals, shopping, family, reports, bills, settings, assistant, subscription
- backend/config — تنظیمات Django
- backend/apps/* — accounts, households, ledger, budgets, shopping, planning, reporting, billing, notifications, support
- docs — ADR، قرارداد API، طراحی، عملیات، نقشه راه، ریسک‌ها و راهنمای انتشار
- .github/workflows — Android CI، Backend CI، Release
- assets/source — منابع تصویر، assets/webp — خروجی‌های بهینه

**قاعده معماری:** featureها مستقل و قابل تست باشند؛ کسب‌وکار در ViewModel/Composable و اعتبارسنجی مالی در UI پراکنده نشود. شروع با Modular Monolith، نه مایکروسرویس بی‌دلیل.

## 10. لایسنس، اشتراک و آمادگی کافه‌بازار

**اصل اصلی:** طراحی هسته محصول از ابتدا برای Entitlement قابل افزودن، اما فروش واقعی فقط پس از آماده‌شدن و آزمایش دقیق جریان بازار.

- ProductPlan و FeatureFlag/Entitlement مستقل از UI و Billing SDK؛ نمونه دسته‌های احتمالی Free، Plus، Family، نه قیمت‌گذاری قطعی.
- امکانات پایه مانند ثبت هزینه و مشاهده داده شخصی نباید با اتمام اشتراک نابود شوند؛ دسترسی به ویژگی‌های پولی بر اساس پاسخ امن سرور اعمال شود.
- Android BillingProvider interface با پیاده‌سازی CafeBazaar و فضای Mock برای تست؛ نسخه توزیع مستقیم می‌تواند provider جداگانه و سازگار با سیاست کانال خود داشته باشد.
- برای بازار، بررسی و انتخاب SDK رسمی Poolakey در فاز ادغام؛ جزئیات قرارداد اشتراک، تأیید رسید، مرجوعی، تمدید، مصرف، بازیابی و الزامات فروشگاه قبل از انتشار مجدد راستی‌آزمایی شوند.
- پرداخت ناموفق، pending، لغو شده، بازپرداخت، اشتراک منقضی و restore روی دستگاه دوم باید تست شوند؛ Client نتیجه خرید را به تنهایی ملاک فعالسازی قرار ندهد.
- کلید امضای release و applicationId از نسخه اول انتشار ثابت بمانند؛ versionCode صعودی، changelog، privacy policy، داده‌های تست و راهنمای بررسی آماده باشد.
- محصول از روز اول برای تغییرات قیمت و محدودیت ویژگی بدون الزام به APK جدید مدل می‌شود؛ ولی سیاست و UI فروشگاه رعایت گردد.
- انتشار با APK امضاشده و در صورت پشتیبانی کانال AAB نیز آماده باشد؛ شکل نهایی artefact مطابق دستورالعمل روز بازار تأیید شود.

## 11. امنیت، حفظ حریم خصوصی، مقیاس و پشتیبانی

- فقط TLS؛ Keystore برای کلیدهای دستگاه؛ توکن‌ها در فضای امن؛ قفل اختیاری بیومتریک/PIN؛ عدم ذخیره کلمه عبور/OTP در Log.
- Room حاوی اطلاعات مالی حساس با انتخاب سازوکار معتبر رمزنگاری محلی و مدیریت کلید؛ Backup و انتقال دستگاه با راهبرد روشن، نه کپی ساده دیتابیس.
- دسترسی سرور فقط با RBAC و بررسی ownership/household membership؛ object-level tests؛ Rate Limit برای OTP و خرید.
- عدم جمع‌آوری داده غیرضروری و عدم ارسال خام گزارش‌های مالی به سرویس آمار؛ مانیتورینگ با شناسه مستعار و حذف PII.
- محدودیت درخواست، لاگ عملیاتی بدون مبالغ و اطلاعات هویتی حساس، Audit برای تغییرات مالی و اشتراک.
- پایگاه داده با backup رمزنگاری‌شده، تمرین restore، تست مهاجرت و نگهداری تعریف‌شده؛ محیط dev/staging/prod ایزوله.
- صفحه سیاست حریم خصوصی، شرایط استفاده، تماس پشتیبانی، درخواست خروجی و حذف داده؛ بازبینی حقوقی و سیاست روز فروشگاه پیش از انتشار عمومی.
- تست بار API، ایندکس گزارش‌ها، pagination و lazy loading برای تراکنش‌های حجیم.

## 12. CI/CD، ساخت APK و کیفیت خودکار

**از فاز صفر:** در Push/PR به main → Gradle dependency validation → ktlint/detekt (با baseline قابل پیگیری) → Unit Tests → Compose tests و Screenshot tests در مراحل مناسب → assembleDebug → آپلود APK Debug در GitHub Actions Artifacts.

**Backend CI:** Ruff/formatter → django check → migrations --check → pytest → تست قرارداد و مجوزها با PostgreSQL سرویس تست.

**مسیر Release:** Tag نسخه → بررسی تست و امنیت → build variant marketRelease (و directRelease در صورت نیاز) → دریافت keystore فقط از GitHub Secrets → Gradle assembleMarketRelease → zipalign/apksigner verification → محاسبه SHA256 → APK امضاشده به‌عنوان artifact و در صورت تصمیم، GitHub Release → مستندات نسخه. هیچ Secret یا Keystore در repo/log ثبت نشود.

**مراحل کانال:** dev/staging/market/direct با تفاوت env و BillingProvider؛ روی سرویس Release کدهای Debug، mock-data و لاگ حساس غیرفعال شوند. خودکارسازی آپلود به پیشخان بازار فقط در صورت دسترسی معتبر API و اجازه صریح، به‌صورت فاز جدا.

**خروجی فنی:** README راه‌اندازی، gradlew قابل اجرا، API example.env، مسیر artifact واضح، ساخت بی‌خطا در CI، نسخه‌بندی semantic/پروژه‌ای و تحویل هر Build قابل رهگیری به Commit SHA.

## 13. استاندارد UX، کارایی و Accessibility

- صفحه Home در ابعاد متداول، مهم‌ترین داده‌ها را بدون اسکرول طولانی نمایش دهد؛ بخش‌های بعدی با اسکرول طبیعی، نه فشرده‌سازی غیرقابل خواندن.
- ثبت تراکنش پایه حداکثر در چند لمس پس از باز شدن فرم؛ صفحه طولانی برای هزینه ساده اجباری نیست.
- برای 1000+ تراکنش Pagination/LazyColumn، گزارش سنگین در background و cache؛ scrolling روان روی موبایل میان‌رده.
- هدف عملکرد آزمایشی: شروع قابل تعامل حدود 2–3 ثانیه روی دستگاه مبنا با داده محلی، و بدون بلوکه شدن تعامل در Sync؛ مقدار واقعی با Macrobenchmark اندازه‌گیری شود.
- هیچ عملیات کاربر بدون بازخورد باقی نماند؛ حالت ذخیره محلی، در انتظار Sync و خطا مشخص باشد.
- Contrast مناسب، قابلیت Screen Reader، کنتراست غیرمتکی به رنگ تنها، بزرگ‌نمایی متن، کاهش انیمیشن، اندازه مناسب لمس و TalkBack.
- Persian localization برای املا، ارقام، واحد تومان، فرمت تاریخ/روز هفته و عدم شکستن متن بلند.

## 14. سناریوهای تست پذیرش ضروری

1. ثبت هزینه ساده آفلاین، بستن برنامه و بازیابی بدون فقدان داده.
2. Sync دوباره همان درخواست، بدون تراکنش تکراری.
3. دو دستگاه هم‌زمان در یک خانواده؛ ایجاد و ویرایش تراکنش‌ها و نمایش درست مانده.
4. حساب خصوصی یک عضو در گزارش عضو دیگر دیده نشود.
5. انتقال 1,000,000 تومان بین دو حساب، جمع دارایی را تغییر ندهد.
6. خرید فروشگاه 2,000,000 تومان با ردیف‌های 700k پروتئین، 500k سبزیجات، 500k برنج و 300k تنقلات، فقط یک بار از حساب کسر شود.
7. حذف/ویرایش تراکنش با آثار دفترکل و گزارش هماهنگ بماند.
8. ثبت پرداخت قسط/بدهی دوبار در هزینه ماه شمرده نشود.
9. ثبت درآمد و هزینه در مرز ماه شمسی، با منطقه زمانی صحیح.
10. بودجه دسته با تراکنش جدید به‌روز و هشدار درست فعال شود.
11. لیست خرید مشترک با تیک هم‌زمان و تبدیل به تراکنش چندردیفی درست کار کند.
12. ورود OTP نادرست/تکرار ارسال/انقضا/قفل موقت.
13. انقضای نشست و خروج از همه دستگاه‌ها.
14. تلاش عضو بدون مجوز برای ویرایش داده خانواده → 403 و ثبت audit.
15. درخواست انقضای اشتراک در شرایط آفلاین با سیاست grace period تعریف‌شده.
16. خرید اشتراک موفق، ناموفق، لغوشده، مرجوعی و restore.
17. Rotate/upgrade نسخه با حفظ دیتابیس Room و توان بازیابی.
18. Font Scale بالا، TalkBack، دستگاه کوچک و بزرگ، RTL و dark mode.
19. Export و حذف حساب بدون خروج داده شخصی عضو دیگر.
20. تست تأخیر، قطعی شبکه، retry و تداخل درخواست‌ها.
21. Release APK در CI واقعاً نصب و روی چند نسخه Android smoke-test شود.
22. هیچ مدل/داده ساختگی در Production به‌عنوان داده واقعی نمایش داده نشود.

## 16. معیار تحویل و روش کار

### Definition of Done هر تغییر

- پیاده‌سازی واقعی + سازگاری Theme/RTL + حالت‌های Empty/Loading/Error/Offline
- تست واحد/سناریویی متناسب، مهاجرت دیتابیس در صورت لزوم، عدم Regression
- اسکرین‌شات یا تست بصری برای صفحه جدید؛ تطبیق با دو موکاپ موبایل مرجع
- اجرای CI موفق و APK خروجی در صورت تغییر Android
- مستندات API و Privacy به‌روز در صورت تغییر قرارداد/داده
- Commit شفاف روی repo و گزارش SHA، فایل‌های تغییرکرده، تست‌های اجراشده و ریسک‌های باقی‌مانده

### دستور کار مراحل بعدی

شروع از فاز 0؛ ابتدا وارسی HEAD و وضعیت GitHub Actions؛ سپس اجرای یک فاز محدود و قابل تست؛ Commit و Push؛ بازبینی عملی؛ گذار به فاز بعد فقط پس از عبور معیارهای پذیرش. درخواست‌های جدید کاربر به‌عنوان Change Request همراه با اثر روی زمان/معماری/Design System در سند ثبت شوند.

### ریسک‌ها و تصمیم‌های باز

- قطعی‌کردن شناسه پکیج (applicationId) **پیش از نخستین انتشار رسمی**؛ انتخاب اولیه تنها پس از تأیید نام نهایی برند/مالک دامنه.
- تعیین زیرساخت استقرار و SMS Gateway، آدرس API و دامنه سیاست حفظ حریم خصوصی؛ هیچ رمز و کلید واقعی در فایل‌های مخزن.
- سیاست Pricing/Feature Limits و محصولات درون‌برنامه‌ای، پس از اعتبارسنجی مدل کسب‌وکار؛ معماری آماده است ولی پلن‌ها هنوز قیمت ندارند.
- نهایی‌کردن فونت مجاز و نمونه‌های WebP اختصاصی؛ دارایی‌های تولیدشده فعلی باید نسخه اصلی و کیفیت مناسب App داشته باشند.
- تأیید الزامات به‌روز بازار و نسخه‌های SDK/Target API در زمان انتشار، نه تکیه بر اعداد ثابت این سند.
- سیاست پشتیبانی از کاربر مهمان/آفلاین و نحوه Merge پس از ثبت‌نام باید پیش از فعال‌سازی Sync نهایی شود.

## 17. اولویت روز شروع

1. ایجاد ساختار پروژه Android Gradle و backend Django در همین repo با build smoke test.
2. افزودن CI حداقلی و تولید APK Debug واقعی به‌عنوان اولین milestone.
3. ثبت فایل‌های مرجع تصویری منتخب و ساخت WebP جیبو و راهنمای توکن‌ها.
4. پیاده‌سازی صفحه Welcome و Home با Compose قابل تعامل و داده local sample مشخصاً برچسب‌خورده به‌عنوان نمونه.
5. آغاز ماژول Money/Ledger و آزمون‌های صحت مالی پیش از اتصال داده واقعی UI.

**نکته:** این سند **نقشه راه اجرای آینده** است. تا زمان ایجاد کد و گذر تست‌ها هیچ‌یک از امکانات فوق «ساخته‌شده» محسوب نمی‌شوند.
